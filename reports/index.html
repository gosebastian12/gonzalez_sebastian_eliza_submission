SEC EDGAR filings summary

Corpus Layout & Patterns

Observed structure under edgar_corpus/ (with manifest.json) is stable enough to drive metadata on every chunk and hybrid retrieval in EdgarHybridRAG—not ad hoc parsing per question at runtime beyond query interpretation.

  • Filename convention: TICKER_10K|10Q[_YYYYQn]_YYYY-MM-DD_full.txt encodes symbol, form, optional fiscal quarter label, and filing date. When the header block is incomplete, ingestion falls back to this pattern so Chroma still gets consistent ticker / form_type / dates for filtering.
  • Leading key-value header: lines such as Company:, Ticker:, Filing Type:, Filing Date:, Report Period:, Quarter:, CIK:, Source:, URL: appear before a row of = characters. Those fields map directly into document metadata used for source labels and Chroma where-style filters at query time (edgar_query_patterns.py aligns user text to the same stored strings, e.g. 10-K vs 10-Q variants).
  • Body shape after the header: exports often place dense machine-tagged numeric blocks first, then the human-readable SEC cover (UNITED STATES SECURITIES AND EXCHANGE COMMISSION, FORM 10-Q / 10-K) and narrative sections with Part / Item headings and pipe-separated financial tables. That predictable mix motivates treating tabular pipe text as first-class context in prompts and lexical scoring—not random noise in a generic PDF dump.

On-disk layout & header parsing: src/backend/data_processing/chunk_and_embed.py (extract_header_metadata, filename fallback). Runtime filters & multi-issuer behavior: edgar_hybrid_rag.py, edgar_query_patterns.py. Default ingest path: repo edgar_corpus/ (override --corpus-dir).

System architecture

Runtime Architecture

Browser submits POST /chat; FastAPI runs EdgarHybridRAG.answer inside run_in_threadpool.

  • Module load: main.py resolves llm-user-prompt.py and imports via importlib; inserts services dir on sys.path.
  • Config reload: fingerprint from dataclasses.asdict(RAGConfig.from_env()); new EdgarHybridRAG when fingerprint changes.
  • Services: LangChain Chroma with host/port + collection; OllamaEmbeddings + ChatOllama with num_predict, num_ctx, timeouts.

Source: src/frontend/main.py, src/backend/services/edgar_hybrid_rag.py, src/backend/services/llm-user-prompt.py

Chunking, Embedding & Vector DB Ingestion

Multi-Stage Chunking Pipeline

build_documents_for_report() builds LangChain Document rows before embedding.

  • Sections: split_into_sections splits on HEADING_RE (PART / ITEM lines).
  • Tables vs prose: split_tables_and_text tags blocks as table or text using pipe/heuristic line detection.
  • Text grouping: split_semantic_text groups paragraphs; subheadings from SUBHEADING_RE start new units.
  • Length cap: split_with_overlap enforces max_chars / overlap_chars (CLI defaults 800 / 100).
  • Ingest: ingest_documents batches embeddings through Ollama and Chroma.add_documents; optional skip by deterministic chunk id.

Source: src/backend/data_processing/chunk_and_embed.py

Findings

Manual Prompt Testing: Scenarios and Behavior

Structured from logs/test_questions.md (prompt inventory). Each branch is a scenario class; nested lines pair a prompt theme with the observed system behavior noted in that log—not benchmark scores.

  • Single-company
    • NVIDIA revenue / growth (~2y). Early runs mixed in other companies; after retrieval changes, chunks stayed NVIDIA-only.
    • JPMorgan CET1 ratio. Exercises a narrow numeric readout on a single ticker using retrieved Tabular data.
  • Multi-company
    • Vague pharma regulatory risks. Broad sector ask; retrieved chunks for all four pharmaceutical companies in the corpus.
    • Apple vs Tesla vs JPMorgan risk comparison. Observed: no Tesla chunks returned—only Apple and JPMorgan material surfaced.
  • Time / filing constraints
    • NVDA data-center commentary, 2024Q3 pinned. Every retrieved chunk traced to NVDA 2024Q3 10-Q—quarter filter held.
    • META trend analysis, "10-K / annual only" in the prompt. Chunks spanned annual reports present in the vector DB (specifically 2026 and 2024 10-K's, 2025 10-K not in corpus).
  • Edge cases & regressions
    • Palantir risks—no Palantir filings ingested. Observed: retrieval still handed the model chunks; answer read as factual despite missing issuer corpus.
    • Fabricated divestiture (Google 10-Q / Pixel sold to Meta). Observed: answer did not use retrieved text to correct the false premise; retrieved chunks skewed to Meta only.
    • Extremely long user question about AAPL, JPM, META, MRK, NVDA, and more. Observed: Model response was short and truncated due to the large number of tokens in the user question. Only AAPL chunks were retrieved. Response generation time increased to ~30 seconds.

Source catalog: logs/test_questions.md. Related implementation: edgar_hybrid_rag.py, edgar_query_patterns.py, rag_reranking.py, chat.html.

Limitations & future improvements

Opportunities for Improvement

  • Quantitative Performance Metrics: Calculating performance metrics such as Mean Reciprocal Rank, Hit Rate, Recall/Precision @K, etc. with libraries such as ragas would help quantify the performance of the system. Such code would be added to evaluation.py.
  • Generation Length: Ollama num_predict caps completion tokens; answers truncate when budget exhausted mid-stream. Larger models would allow for longer generation lengths even when user questions are very long.
  • Context Length: The current context length is 4096 tokens. Larger models would allow for longer context lengths and thus more retrieved chunks.
  • Unit Testing: Development of unit tests would help ensure the system is working as expected, especially all steps of chunking process.
  • User-Provided Documents: A new feature could be added to allow users to upload their own documents to be ingested into the vector database.
  • Better Component Modularity: Reliance on ollama models and chroma database is strict and could be better generalized to allow for more flexibility in the system.
  • Handling of 10-K and 10-Q Diagrams: Any images present in company reports are not stored in corpus .txt/ files. Their inclusion would allow system to answer any user questions about them by leveraging multi-modal LLM's.
  • Storing Chat History: Inclusion of a backend SQL database in architecture would allow for storing/caching chat history and retrieving it later.
  • Safeguards Against False Information: The system currently not able to detect and correct false information in user questions.
